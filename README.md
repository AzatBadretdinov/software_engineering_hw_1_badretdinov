# ВышКат — домашнее задание №1 по КПО

Консольное приложение на Go для учёта парка кикшеринга.

## Что реализовано

- добавление транспорта в активный парк только после техосмотра;
- принятие и отклонение транспорта сервисом техосмотра;
- подсчёт количества транспортных единиц;
- суммарное суточное энергопотребление всех энергопотребляющих объектов на балансе;
- выбор прокатной техники для новичков по правилу `BeginnerEase >= 6`;
- учёт вещей на балансе;
- вывод наименований и инвентарных номеров всей техники и вещей;
- консольная демонстрация всех основных сценариев;
- DI-контейнер на `go.uber.org/dig`;
- подмена техосмотра через DI в тестах;
- юнит-тесты в стиле Arrange / Act / Assert.

## Запуск

Требуется Go 1.23+.

```bash
go mod download
go run ./cmd/vyshkat
```

Тесты и покрытие:

```bash
go test ./... -cover
```

Для общего coverage-профиля:

```bash
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out
```


## Доменная модель

### Интерфейсы

`domain.InventoryItem`

```go
type InventoryItem interface {
    Name() string
    InventoryNumber() string
}
```

Абстракция для всего, что ставится на баланс и имеет инвентарный номер.

`domain.EnergyConsumer`

```go
type EnergyConsumer interface {
    DailyEnergyKWh() float64
}
```

Интерфейс реализуют только реальные потребители энергии. Например, `Scooter`, `ElectricBike`, `ChargingStation`. Обычный `Bicycle` и `Helmet` его не реализуют.

`domain.Transport`

```go
type Transport interface {
    InventoryItem
    BeginnerEase() int
    IsOperational() bool
}
```

Любой новый вид транспорта достаточно сделать совместимым с этим интерфейсом. Код `fleet.Service` при этом менять не требуется.

### Транспорт

- `Scooter` — транспорт + потребитель энергии;
- `Bicycle` — транспорт без энергопотребления;
- `ElectricBike` — транспорт + потребитель энергии.

### Вещи

- `Helmet` — инвентаризируемая вещь;
- `ChargingStation` — инвентаризируемая вещь + потребитель энергии.

В Go нет наследования классов, поэтому небольшая иерархия реализована идиоматично через композицию (`inventoryBase`, `transportBase`) и интерфейсы. Это сохраняет общее поведение без искусственной имитации классического наследования.

## Техосмотр

Реальная реализация — `servicecenter.ServiceCenter`.

Перед добавлением транспорта `fleet.Service.AddTransport` обязательно вызывает зависимость:

```go
type VehicleInspector interface {
    Inspect(domain.Transport) bool
}
```

`fleet.Service` не создаёт `ServiceCenter` самостоятельно. Зависимость передаётся через конструктор:

```go
func NewService(inspector VehicleInspector) *Service
```

Реальный `ServiceCenter` принимает исправный (`IsOperational() == true`) транспорт и отклоняет неисправный. Это небольшое правило выбрано сознательно: условие ДЗ не задаёт более сложную процедуру техосмотра.

## Dependency Injection и DI-контейнер

Composition root расположен в `internal/bootstrap/container.go`.

Используется `go.uber.org/dig`. Контейнер регистрирует:

1. реализацию `fleet.VehicleInspector`;
2. `fleet.Service`;
3. `io.Writer` для консольного вывода;
4. `console.App`.

Контейнер используется только в composition root. Бизнес-код не обращается к container/service locator напрямую.

В тестах `fleet.Service` получает `fakeInspector`, поэтому решение техосмотра полностью контролируется тестом:

```go
type fakeInspector struct {
    decision bool
}

func (f *fakeInspector) Inspect(domain.Transport) bool {
    return f.decision
}
```

Так отдельно проверяются сценарии «принять» и «отклонить» без зависимости от настоящего `ServiceCenter`.

# SOLID

## S — Single Responsibility Principle

Наиболее заметные границы ответственности:

- `domain` описывает данные и минимальные доменные контракты;
- `servicecenter.ServiceCenter` выполняет техосмотр;
- `fleet.Service` ведёт активный парк, баланс и отчёты;
- `console.App` отвечает только за демонстрационный ввод/вывод;
- `bootstrap` собирает зависимости.

То есть причины изменения разделены: изменение правил техосмотра не требует переписывать консоль или сущности, а изменение формата вывода не затрагивает бизнес-логику.

## O — Open/Closed Principle

`fleet.Service` работает с `domain.Transport`, `domain.InventoryItem` и `domain.EnergyConsumer`, а не с перечнем конкретных типов.

Например, чтобы добавить новый `Monowheel`, достаточно реализовать нужные методы `Transport` и, если он электрический, `EnergyConsumer`. Методы подсчёта энергии, техосмотра и отбора для новичков не требуют `switch` по видам транспорта.

## L — Liskov Substitution Principle

В Go нет иерархии классов в классическом смысле. Подстановка проявляется через интерфейсы: любая реализация `domain.Transport`, соблюдающая его контракт, может быть передана в `fleet.Service.AddTransport` без изменения сервиса.

Проект не заставляет обычный велосипед притворяться энергопотребляющим устройством, поэтому нет заглушечных методов и нарушений контракта.

## I — Interface Segregation Principle

Интерфейсы специально маленькие и разделены:

- `InventoryItem` — имя и инвентарный номер;
- `EnergyConsumer` — только расход энергии;
- `Transport` — только свойства прокатного транспорта;
- `VehicleInspector` — только техосмотр.

Поэтому `Helmet` не обязан иметь метод расхода энергии, а `Bicycle` не содержит фиктивный `DailyEnergyKWh() == 0`.

## D — Dependency Inversion Principle

Это наиболее явно применённый принцип.

`fleet.Service` зависит от абстракции `VehicleInspector`, а не от конкретного `servicecenter.ServiceCenter`. Конкретная реализация выбирается снаружи и передаётся через DI-контейнер/constructor injection.

Это одновременно позволяет легко заменить реальный техосмотр на fake в юнит-тестах.

# Ответы на обязательные вопросы

## 1. Какой принцип SOLID применён наиболее явно и где?

**DIP** в `internal/fleet/service.go`.

`fleet.Service` хранит `VehicleInspector` и не знает о конкретном `servicecenter.ServiceCenter`. В `internal/bootstrap/container.go` DI-контейнер связывает абстракцию с реальной реализацией.

## 2. Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?

Сознательно ограничен **OCP на уровне демонстрационного `console.App`**: конкретные примеры `Scooter`, `Bicycle`, `Helmet` и `ChargingStation` создаются прямо в консольном сценарии. Если нужно продемонстрировать новый тип, этот демонстрационный файл придётся изменить.

Это приемлемо, потому что `console.App` — composition/demo layer, а не универсальный фабричный механизм. В доменной и бизнес-логике новый тип транспорта добавляется без массовой правки. Добавлять Factory/Abstract Factory только ради нескольких фиксированных демонстрационных объектов было бы лишним усложнением и противоречило бы KISS/YAGNI.

## 3. Что произойдёт при расширении программы?

### Новый вид транспорта

Основная бизнес-логика не сломается. Новый тип реализует `domain.Transport`; если потребляет энергию — дополнительно `domain.EnergyConsumer`. `fleet.Service` менять не нужно.

### Сотрудник

Сотрудники по условию не ставятся на баланс, поэтому они не должны реализовывать `InventoryItem`. Для них можно добавить отдельную модель/сервис, не меняя существующий контракт баланса.

### Склад запчастей

Сами инвентаризируемые запчасти могут реализовывать `InventoryItem`. Если появятся складские операции (остатки, выдача, приёмка), их следует вынести в отдельный сервис, а не расширять `fleet.Service` несвязанной ответственностью.

## 4. Какой тест фиксирует решение техосмотра и правило «для новичков»? Как подменяется зависимость?

Файл `internal/fleet/service_test.go`:

- `TestAddTransportAcceptedByInjectedInspector`;
- `TestAddTransportRejectedByInjectedInspector`;
- `TestBeginnerFriendlyTransportsUsesThresholdSix`.

В первых двух тестах реальный техосмотр заменён `fakeInspector`, который реализует тот же `VehicleInspector`. Fake передаётся в `NewService` через constructor injection.

## 5. Что сделал ИИ?

ИИ использовался для помощи в разработке и проверке юнит-тестов: подбора тестовых сценариев, проверки граничных случаев и анализа покрытия. Архитектура проекта, доменная модель и основная реализация приложения были выполнены самостоятельно.

# Проверяемые сценарии

1. исправный электросамокат проходит техосмотр и попадает в парк;
2. неисправный электровелосипед отклоняется и не попадает ни в парк, ни на баланс;
3. обычный велосипед проходит техосмотр и учитывается без фиктивного энергопотребления;
4. шлем и зарядная станция ставятся на баланс;
5. энергия считается только для объектов, реализующих `EnergyConsumer`;
6. новичкам показывается только транспорт с `BeginnerEase >= 6`;
7. выводится общий инвентарный список техники и вещей;
8. одинаковые инвентарные номера запрещены.
